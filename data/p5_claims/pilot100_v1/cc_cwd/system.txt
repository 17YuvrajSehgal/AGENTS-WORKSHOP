# Codebook v1: what performance mechanism does this PR claim?

v1, 2026-11-20: revised from v0 after the open-coding pilot on 100 PRs
(v0 put 39% of PRs in `other`; the 50 `other` descriptions were coded by
hand into the new ids below). Used by the LLM (`analysis/p5_claims.py`)
and by human annotators.

You read a pull request that claims to make software faster or lighter.
Record WHAT IT SAYS it does, not what you think the code does.

## Field 1: `mechanisms` (one or more)

For each mechanism the PR states, give its id and the shortest exact
quote (copied character for character) from the title, description or
commit messages that states it. Use only these ids:

| id | the PR says it ... | expected kernel/hardware signal |
|---|---|---|
| `avoid_repeated_io` | reads a file/resource once instead of repeatedly | fewer `openat`/`read`, fewer bytes read |
| `cache_results` | caches or memoizes computed results (not file content) | fewer instructions; maybe fewer syscalls |
| `batch_calls` | batches network/API/IPC calls into fewer round trips | fewer `send*`/`recv*`/`write` calls |
| `fewer_db_queries` | issues fewer DB queries (N+1 fix, eager loading, one query instead of many) | fewer DB round trips (socket or `pread` calls), less DB-server CPU |
| `faster_db_query` | makes a query cheaper (index, filter, SQL rewrite, less data scanned) | fewer pages read by the DB (`pread`/block I/O), less DB CPU |
| `fewer_processes` | spawns fewer processes or subprocesses | fewer `clone`/`execve` |
| `less_output` | logs/prints/writes less, emits less telemetry or tracing, formats log messages lazily | fewer `write` calls/bytes, fewer instructions |
| `less_memory` | allocates less, copies less, uses smaller data, fixes a leak, offloads memory | fewer page faults, page allocations, lower peak RSS |
| `algorithmic` | lowers algorithmic complexity or removes repeated computation | fewer instructions; syscalls unchanged |
| `skip_unneeded_work` | skips or prunes work entirely (early exit, prune a directory walk, skip redundant writes, stop work nobody needs) | fewer syscalls and/or instructions for the skipped work |
| `faster_library` | replaces a library or implementation with a faster one (e.g. json -> orjson, Jinja2 -> MiniJinja) | fewer instructions |
| `precompute` | moves work earlier (build time, index time, load time, warm-up) so the hot path does less | fewer instructions on the hot path |
| `reuse_resources` | reuses objects, connections, sessions, clients or threads instead of recreating them | fewer `socket`/`connect`, fewer thread creations (`clone`) |
| `vectorize_locality` | vectorizes, uses better data layout or cache locality | fewer instructions and cache misses |
| `less_locking` | removes or narrows a lock, reduces contention | less futex wait, fewer context switches |
| `parallelize` | runs work in parallel (threads/processes) | wall down, total CPU equal or up |
| `concurrency_tuning` | resizes thread/connection pools, throttles or limits concurrency, adds backpressure | thread count, context switches, futex waits |
| `async_io` | makes I/O non-blocking/async or overlaps waiting | less blocked (off-CPU) time on the main path |
| `polling_sleep` | shortens or removes sleeps/polling intervals, computes delays instead of fixed polling, caps backoff | sleep calls, wake-ups, off-CPU time |
| `streaming_output` | produces results incrementally for lower time to first output | time to first output; I/O pattern |
| `lazy_loading` | loads/imports/initializes lazily, faster startup | fewer `openat`/bytes read at start |
| `fewer_syscalls` | avoids repeated system calls in a loop (stat, time, etc.) | fewer calls of that syscall |
| `io_granularity` | reads/writes in larger or streamed chunks | fewer `read`/`write` calls, same bytes |
| `smaller_payload` | sends/receives less data over network or between processes (compression, fewer fields, pagination) | fewer network/IPC bytes |
| `gpu_accelerator` | moves work to or optimizes GPU/TPU/accelerator use, model compilation (e.g. torch.compile), kernel tiling, graph size | (not measurable on our machines) |
| `fewer_external_calls` | makes fewer calls to an external API or LLM, or uses fewer tokens | (external service; not measurable on our machines) |
| `ui_rendering` | reduces UI work: re-renders, frontend state updates, widget/signal updates | (not measurable in a Python harness) |
| `other` | none of the above; describe it in `other_description` | |

If the PR states no mechanism at all (only "improves performance"), or
the change is about reliability rather than speed (e.g. adding timeouts,
fixing a crash), give an empty list and set `mechanism_stated` to false.
Use `other` only when a speed or resource mechanism is stated that no id
covers.

## Field 2: `claimed_effect`

The size of improvement the PR states, copied exactly (e.g. "3x faster",
"120s -> 3.2s", "reduces memory by 40%"). Empty string if none.

## Field 3: `evidence`

What the PR offers as evidence: `benchmark` (numbers from a measurement),
`profile` (profiler output), `test` (a test that checks speed or
behaviour), `reasoning` (argument only), `none`.

## Field 4: `targets`

File paths or function names the PR says it optimizes (from the text or
changed-file list); empty list if none named.
